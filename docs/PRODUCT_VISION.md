# Instant Space 产品落地文档：全球旅行攻略空间

> 版本：2026-07-09  
> 当前定位：先聚焦“全球旅行攻略空间”，再逐步扩展实时共享体验、3D 场景和 AI 运营。  
> 一句话：**每一个真实旅行地点，都可以有一个可通过地图、链接或二维码进入的数字攻略空间。**

---

## 1. 产品定位

Instant Space 不再泛化为“任何即时空间”，当前阶段聚焦为：

> **全球旅行攻略与共享体验空间平台**

用户打开网站后，第一屏不能只丢一张地图。地图很酷，但如果没有一句话说明价值，用户不知道为什么要看、为什么要点、为什么要创建空间。

第一屏应该先讲清楚产品价值，再让地图承接探索：

> **发现全球旅行攻略空间，扫码进入真实地点的共享体验。**

辅助说明可以是：

> 在地图上找到景点、餐馆和城市空间，查看攻略、加入社群、分享链接或二维码给朋友；未来还能进入同一个 3D 场景一起体验。

首屏 UX 原则：

- **5 秒内讲清楚**：用户一眼知道这是全球旅行攻略空间，不是普通地图。
- **一个主行动**：搜索旅行空间；创建空间和浏览攻略作为次级行动。
- **地图作为证明和探索工具**：地图仍然是视觉核心，但不能替代价值文案。
- **必须有视觉钩子**：首屏需要图片化/插画化表达，例如地图点位、手机扫码、二维码、攻略卡片、朋友头像和未来 3D 标签；不能只有文字和按钮。
- **轻量动效**：使用浮动卡片、点位脉冲、路线高亮、手机/二维码微动效来表达“真实地点 + 扫码 + 共享体验”，但要尊重 `prefers-reduced-motion`。
- **渐进展示**：首屏只放价值、搜索、关键入口；空间列表、筛选、地图控制放到探索面板或菜单里。
- **移动端优先**：手机上首屏文案要短，按钮要大，避免多个浮层叠在地图上。
- **真实场景提示**：明确告诉用户可以扫码、分享给朋友、未来进入 3D 共享体验。

地图上的点不是普通文章，也不是泛社区频道，而是一个个真实地点对应的 **Space / 空间**。

空间承载三类能力：

1. **攻略内容**：这个地点怎么玩、吃什么、路线怎么走、注意事项是什么。
2. **社群连接**：围绕这个地点加入 Discord/QQ 讨论组，获取实时信息和密码。
3. **共享体验入口**：未来通过链接/二维码/3D 场景，让远方朋友进入同一个数字空间一起交流。

## 2. 核心场景

### 2.1 旅行前：找攻略

用户准备去一个城市或景点：

1. 打开地图或搜索地点。
2. 找到对应空间。
3. 查看空间下的多份攻略：景点攻略、美食攻略、路线攻略、避坑提示。
4. 收藏或分享空间链接。

### 2.2 旅行中：进空间

用户到达真实地点：

1. 扫描店铺/景点/朋友分享的二维码，或打开空间链接。
2. 进入该地点的空间详情。
3. 查看攻略、实时公告、进入社群或聊天。
4. 如果是私密空间，输入主理人提供的密码。

### 2.3 和朋友异地共享体验

例子：

> 我先去了某个景点旁边的一家餐馆吃饭。  
> 我把餐馆空间的链接或二维码发给朋友。  
> 朋友扫码后进入这个餐馆的数字空间，看到同一份攻略、现场信息、未来还可以进入 3D 场景和我“面对面”一起分享体验。

这是产品的长期差异化方向，但当前实现必须先打好 Space、Guide、QR/Link 的数据基础。

## 3. 核心对象定义

### 3.1 Space / 空间

**空间是地图上的主对象。**

一个 Space 代表一个真实旅行地点的数字入口，可以是：

- 景点：外滩、故宫、白云山。
- 餐馆：某家火锅店、咖啡馆、当地小吃店。
- 城市/街区：宽窄巷子、老城区、夜市。
- 活动地点：临时展览、旅行聚会、快闪活动。

空间负责回答：

- 这个地点在哪里？
- 谁创建和维护它？
- 是否公开？是否需要密码？
- 有哪些相关攻略？
- 如何进入社群或聊天？
- 未来如何通过 QR/3D 场景进入共享体验？

### 3.2 Guide / 攻略

**攻略是空间下面的内容资产。**

一份 Guide 是结构化内容，不是随便堆一段富文本。它可以包括：

- 概览
- 景点
- 美食
- 路线
- 交通
- Tips
- 图片

一个空间可以对应多份攻略：

```text
Space: 外滩
├── Guide: 外滩半日游路线
├── Guide: 外滩拍照机位
├── Guide: 外滩附近餐馆推荐
└── Guide: 外滩夜景避坑指南
```

同时，攻略也允许不绑定空间：

```text
Guide.space_id = NULL
```

这类攻略叫 **独立攻略**，用于：

- 还没创建对应空间的城市/区域攻略。
- 跨多个地点的主题攻略。
- 运营先写内容，后续再绑定空间。

### 3.3 Community / 社群

当前阶段，社群先借助 Discord/QQ：

- 总频道负责公告和空间列表。
- 省份/地区板块负责组织地点。
- 每个空间可以有自己的讨论组。
- 主理人审核后，成员才获得实时密码或更新。

后续可以逐步迁移到站内实时聊天和 AI 助手。

### 3.4 QR / Link 入口

QR 和链接是增长入口，不是附属功能。

每个空间都应该天然拥有：

- 可分享链接。
- 可生成二维码。
- 可贴在餐馆、景点、活动现场。
- 可由朋友直接转发。

用户扫码进入的应该是 **Space 详情页**，而不是单篇攻略页。攻略只是空间里的内容之一。

## 4. Space 与 Guide 的关系

### 4.1 数据关系

```text
Space 1 : N Guide
Guide.space_id optional
```

含义：

- 一个空间可以有多份攻略。
- 一份攻略最多绑定一个空间。
- `space_id = NULL` 表示独立攻略。
- 已保存的攻略再次保存应该更新同一个 guide，而不是创建重复攻略。

### 4.2 产品逻辑

用户写攻略时必须能明确选择：

1. **绑定到某个已有空间**  
   适合“我正在给这个景点/餐馆补攻略”。

2. **先写独立攻略**  
   适合“我不想绑定现在这五个空间，我要单独写一份城市/路线/主题攻略”。

3. **从空间管理入口写攻略**  
   默认预选当前空间，不需要用户再猜对应哪个空间。

### 4.3 权限逻辑

普通用户：

- 可以创建空间。
- 可以编辑自己创建的空间。
- 可以创建攻略。
- 可以编辑/删除自己创建的攻略。
- 不能编辑别人创建的空间和攻略。

管理员 / super_admin：

- 可以管理所有空间。
- 可以管理所有攻略。
- 可以处理驻留、异常、内容运营。
- `/admin` 是后台管理入口，不是普通用户功能。

## 5. 地图到底显示什么

### 5.1 当前原则：地图主显示 Space

地图上的主点位应该是 **空间**，不是攻略。

原因：

- 地图天然表达“地点”。
- Space 是真实地点的数字入口。
- Guide 是内容，可以挂在空间下，也可以被搜索/列表发现。
- 如果地图直接显示所有攻略，同一个地点多份攻略会产生重复点、混乱点和难以管理的关系。

### 5.2 Guide 如何被发现

攻略应该通过这些入口被发现：

- 空间详情页里的“相关攻略”。
- 攻略列表页。
- 搜索结果。
- 后续可选的“攻略图层”，但默认不打开。

### 5.3 Space 详情页应该承载什么

空间详情页是用户扫码/点击地图后的落点，至少包含：

1. 空间基础信息：名称、位置、类型、状态。
2. 攻略列表：该空间下所有可见攻略。
3. 写攻略入口：有权限时可以为该空间新增攻略。
4. 社群入口：Discord/QQ。
5. 私密访问入口：密码验证、聊天入口。
6. 分享入口：链接和二维码。
7. 未来 3D/共享体验入口。

## 6. 管理空间时必须管理相关攻略

“我的空间 / 管理空间”不是只改空间名称和密码，还必须能看到这个空间下的攻略。

管理空间弹窗/页面应该包括：

```text
Manage Space
├── 空间基础信息
├── 地图位置与地址
├── 密码 / 热点名
├── 生命周期：关闭、重开、删除/归档、驻留申请
├── 分享：链接 / 二维码
└── 相关攻略
    ├── 写新攻略（自动绑定当前空间）
    ├── 已绑定攻略列表
    ├── 查看攻略
    ├── 编辑攻略（作者或管理员）
    └── 删除/归档攻略（作者或管理员）
```

这样用户从“管理某个空间”进入时，不会再困惑“我要写的攻略到底对应哪个空间”。

## 7. 攻略编辑器落地规则

攻略编辑器采用结构化对象：

```text
Guide {
  guide_type,
  category,
  title_zh,
  title_en,
  summary_zh,
  summary_en,
  province,
  city,
  district,
  spot_name,
  images: Vec<String>,
  sections: Vec<Section>,
  status,
  featured,
  space_id: Option<Uuid>
}

Section {
  id,
  section_type,
  title_zh,
  title_en,
  content_zh,
  content_en,
  images: Vec<String>
}
```

规则：

- 顶层由一个 Guide 对象持有，不把每个字段拆散成不可追踪状态。
- 新建后第一次保存生成 guide id。
- 后续保存必须 PUT/更新同一个 guide。
- 保存草稿、发布、归档都是同一个 guide 的状态变化。
- `space_id` 可为空，但一旦从空间入口创建，应自动带上当前空间。

## 8. 当前阶段产品优先级

### P0：先把逻辑闭环做对

1. 地图默认显示空间。
2. 空间详情展示相关攻略。
3. 管理空间可以管理相关攻略。
4. 写攻略时可以选择绑定空间或独立攻略。
5. 普通用户只能管理自己的空间/攻略。
6. admin/super_admin 可以管理全部。
7. 同一攻略重复保存不能生成多份重复数据。

### P1：分享与二维码

1. 每个空间生成分享链接。
2. 每个空间生成二维码。
3. 空间详情页适合作为扫码落地页。
4. 二维码后续可用于餐馆、景点、活动现场。

### P2：实时共享体验

1. 空间内聊天升级为 WebSocket。
2. 密码版本与私密空间权限继续保留。
3. 增加在线人数和实时状态。
4. 为 3D 场景入口预留结构。

### P3：AI 辅助运营

1. AI 帮 admin 发现重复空间、低质量攻略、异常内容。
2. AI 帮主理人整理攻略草稿。
3. AI 帮用户根据地点生成初版攻略结构。
4. AI 不替代权限系统，只作为后台/编辑辅助。

---

## 9. 不做什么

为了避免产品继续发散，当前阶段先不做：

- 不把首页做成泛社区信息流。
- 不让地图默认显示所有攻略点。
- 不把 admin 理解成“所有内容必须人工审核”。
- 不把 3D 场景提前做成主功能。
- 不把私密空间、社群、攻略做成互相割裂的三套系统。

---

## 10. 落地验收口径

当一个新用户打开产品时，应该能理解：

1. 这里是一张全球旅行地图。
2. 地图上的点是旅行地点的数字空间。
3. 点开空间可以看攻略、进社群、分享给朋友。
4. 我可以创建一个地点空间。
5. 我可以为自己的空间写多份攻略。
6. 如果我只是想写一份独立攻略，也可以不绑定空间。
7. 管理员只在后台管理全局数据，不干扰普通用户主流程。

如果用户仍然问“空间和攻略到底是什么关系”，说明产品没有落地成功。
