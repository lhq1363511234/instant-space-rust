## 0. 核心认知（之前文案写不好的根因）

**空间 = 任何真实地点的数字入口，不只是旅游景点。**
任何人都可以把自己长期所在的真实地点变成一个空间：
- 公司主 → 以公司为点建一个空间
- 餐馆老板 → 建一个美食空间
- 常去公园的人 → 建一个公园空间
- 景点主理人 → 维护一个景点空间

空间是那个地点的「数字分身 + 主页 + 留言簿 + 社群门口」，通过地图 / 链接 / 二维码进入。
「攻略」只是空间里的一类内容，不是全部。

## 1. AI Agent + 空间/攻略对外 API（作者自用，已完成 2026-07-30）

- 目的：作者本人（**暂不开放给普通用户**）用 AI agent 程序化创建空间、写详细好看的「志」、管理空间。
- 这轮**只做带鉴权的 REST API**，不接大模型；agent 以后由作者自己拿 key 调。
- 鉴权：**API Key**，绑定到某个用户身份，有 scope + 限流；agent 创建的内容归属到该用户。
- 端点（初版设想，落地时再定稿）：
  - `POST   /api/spaces`            创建空间
  - `PATCH  /api/spaces/:id`        管理/更新空间
  - `POST   /api/guides`            创建志（攻略），可绑定 space_id
  - `PATCH  /api/guides/:id`        更新志
  - `GET    /api/spaces` / `GET /api/guides`  读取
- 安全要求（务必）：Key 哈希存储、最小 scope、限流、审计；不得把 Leptos Server Functions 直接当公共协议（见 SITE_MODULE 文档 P3）。

## 2. 「攻略」升级为「空间详情页」，按空间类型分内容（先做）

### 2.1 命名
- 中文：原「攻略」→ **「志」**（空间志 / 为这个空间写志）。契合宋式美学与地方志语感，能涵盖交通/公司/公园等非旅游类型。
- 英文：保留 `Guide`（待用户最终确认，也可能用 Record）。
- 动作文案：「创建攻略」→「**写一篇志**」/「为这个空间写志」。

### 2.2 空间类型
- **类型可自定义**（用户已设置好），不写死枚举。
- 「志」的板块按**当前空间类型动态适配**，自定义类型要有兜底板块。
- 示例：
  - 交通类：换乘 / 出口 / 时刻 / 接驳
  - 餐馆类：招牌菜 / 营业规律 / 排队
  - 公司/机构类：这是做什么的 / 怎么找到 / 主理人
  - 公园/景点类：路线 / 时段 / 看点

### 2.3 详情页信息架构 = 卡片墙（不是从上到下长滚动）
进入空间 = 一面卡片墙，每张卡「点开才进」，首屏保持克制：

```
顶部：空间头（封面 · 名称 · 类型 · 在线人数 · 扫码分享）

关于这个空间（一个「关于」区，并排三张入口卡）：
  ├─ 简介卡   → 点开：这空间是什么、为什么建、性质/标签（简介卡片墙）
  ├─ 主理人卡 → 点开：主理人介绍 + 发展史/沿革（时间线卡片）
  └─ 故事卡   → 点开：各种人留下的故事（留痕/胶囊那条线）

同级另外两个主入口卡：
  ├─ 志 卡    → 点开：按空间类型分板块的实用内容
  └─ 讨论卡   → 点开：实时聊天/社群（已是独立页 /inspace/spaces/:id/chat）
```

- 「简介 / 主理人+发展史 / 故事」合并进同一个 **「关于」区**，各是一张入口卡，点开进各自的卡片墙/详情。
- **故事暂不并入讨论区**，是独立的一张卡。
- 手机端：卡片单列纵向排，点开进子页/抽屉。
